# Alexandria MCP Server

## Summary
- Build a shared Go MCP server over the existing Alexandria services and expose it through both standard MCP transports: Streamable HTTP on the existing app and a separate stdio binary.
- Keep v1 backend-focused: library operations first, reader data second, no UI-driving features from `ReaderView`.
- Allow only safe writes in v1: book metadata updates, metadata refresh, list management, and reading progress. Do not expose upload, delete, cover/file binary transfer, or TTS/display preferences.

## Public Interfaces
- Add an authenticated MCP HTTP endpoint at `/mcp` on the existing Go server. Register it only when `MCP_HTTP_TOKEN` is configured.
- Add a separate `mcp-server` binary that boots the same app wiring and serves the same MCP feature set over stdio.
- Add config for:
  - `MCP_HTTP_TOKEN`: deployment-scoped bearer token for the HTTP transport
  - `MCP_OWNER_USERNAME`: optional owner identity for user-scoped tools; if unset, auto-resolve only when exactly one user exists
- Expose these MCP tools:
  - `books.search`, `books.get`, `books.update`, `books.refresh_metadata`, `books.list_authors`, `books.list_genres`
  - `lists.list`, `lists.create`, `lists.update`, `lists.get_items`, `lists.add_book`, `lists.remove_book`
  - `reader.get_manifest`, `reader.get_section`, `reader.get_progress`, `reader.save_progress`
- Expose read-only resource templates:
  - `alexandria://books/{id}`
  - `alexandria://books/{id}/reader/manifest`
  - `alexandria://books/{id}/reader/sections/{section_id}`
  - `alexandria://books/{id}/progress`
  - `alexandria://lists/{id}`
  - `alexandria://lists/{id}/items`
- Resource payloads should be structured JSON text only. Reader section resources should return the existing section metadata plus HTML, not raw file blobs.

## Implementation Changes
- Create one shared MCP registration layer using the official Go SDK so tool/resource definitions are authored once and reused by both transports.
- Mount the SDK’s Streamable HTTP handler inside the existing Go server via an HTTP-to-Fiber adapter so `/mcp` shares the current deployment, port, and service wiring.
- Guard `/mcp` with bearer-token auth using `Authorization: Bearer <MCP_HTTP_TOKEN>`. Missing or invalid token returns `401` before JSON-RPC handling.
- Keep stdio transport local-only and unauthenticated at the MCP layer; it runs as the trusted owner integration.
- Resolve user-scoped operations like lists and progress against a single owner identity:
  - Use `MCP_OWNER_USERNAME` when set
  - Otherwise auto-select the only existing user
  - If multiple users exist and no owner is configured, return a clear configuration error for user-scoped tools/resources
- Keep the MCP layer thin: it should call existing Alexandria services and reuse current validation/error semantics rather than creating parallel business logic.
- Skip MCP prompts, sampling, and binary/file-upload workflows in v1.

## Test Plan
- Add MCP transport tests for both `/mcp` HTTP and stdio initialization.
- Verify HTTP auth behavior: valid bearer token succeeds, missing/invalid token returns `401`.
- Verify tool discovery only includes the intended v1 surface and omits upload/delete tools.
- Verify happy-path tool calls for:
  - searching books and fetching one book
  - updating safe book fields and refreshing metadata
  - creating/updating lists and adding/removing books
  - reading manifest/section data
  - saving progress and reading it back
- Verify owner-resolution behavior:
  - one-user deployment works without `MCP_OWNER_USERNAME`
  - multi-user deployment without `MCP_OWNER_USERNAME` fails only on user-scoped operations with an actionable error
- Verify resource reads return the expected JSON shapes for book, list, manifest, section, and progress templates.

## Assumptions
- v1 HTTP auth will use a deployment-scoped bearer token, not full OAuth. This is a deliberate simplification for a trusted self-hosted deployment, while keeping a later upgrade path open if wider MCP interoperability is needed.
- v1 reader exposure is backend data only. It will surface manifest/section/progress, not browser-only behaviors like TTS state, theme settings, or iframe navigation state.
