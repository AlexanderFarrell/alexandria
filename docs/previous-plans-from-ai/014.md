# Reader Chrome and Mobile Polish

## Summary
- Polish the reader UI only; no backend, API, or schema changes.
- Keep the current reader functionality intact, but redesign the top chrome and responsive behavior so desktop stays calm and readable while mobile becomes much more focused.
- Target files: [ReaderView.vue](/home/alexander/Projects/alexandria/client/src/views/ReaderView.vue), [NavBar.vue](/home/alexander/Projects/alexandria/client/src/components/NavBar.vue), and shared button spacing in [style.css](/home/alexander/Projects/alexandria/client/src/style.css) only if needed for consistency.

## Implementation Changes
- Top chrome:
  - Keep the current two-bar structure on the reader route, but make it feel intentional as one slim stack.
  - Reduce reader-header height, padding, and visual weight; tighten button sizing and spacing; improve title hierarchy and alignment.
  - Keep richer metadata on desktop: title plus author/chapter stack.
  - Collapse metadata hard on mobile: title-only or title with a very short subtitle, no tall stacked block.
  - Move progress from a loose text fragment into a compact chip/badge in the top chrome.
- Reader controls:
  - Desktop keeps visible controls in the header, but with calmer density and more even grouping.
  - Mobile top row keeps only primary controls visible: back, contents, read aloud, settings, and compact progress.
  - Secondary mobile controls move out of the always-visible header:
    - paragraph picking
    - voice/rate/pitch/volume
    - theme customization
  - Settings become an inline panel on desktop and a bottom sheet/drawer on mobile.
- Navbar:
  - Keep `NavBar compact-mobile` on the reader route, but make the compact reader variant slimmer.
  - Hide non-essential nav links on small screens and reduce the sign-out button footprint so the stacked top chrome does not dominate the viewport.
- Footer:
  - Keep the previous/progress/next footer on mobile, but compress it.
  - Ensure the footer wraps cleanly without crowding the reading area and remains secondary to the top controls.
- Styling tone:
  - Push the reader chrome toward “editorial calm”: quieter borders, cleaner spacing, stronger title typography, less button noise.
  - Improve truncation rules so long titles do not create awkward multi-line toolbar layouts.
  - Rebalance breakpoints around the current `980px`, `720px`, and `480px` rules instead of inventing a new responsive system.

## Interfaces / Behavior
- No API changes.
- No persistence changes.
- No TTS behavior changes beyond where controls are presented.
- Add only local UI state if needed for the mobile settings sheet/drawer and mobile secondary actions tray.

## Test Plan
- Desktop:
  - Long title + author + chapter still read well in the header.
  - Header controls remain aligned and do not wrap awkwardly at common laptop widths.
  - Settings panel still opens without pushing the reader into a broken layout.
- Mobile:
  - Top chrome fits cleanly on narrow widths without the metadata stack dominating height.
  - Contents drawer, settings sheet, and TTS actions are reachable with one hand and do not overlap unusably.
  - Footer remains usable and visually subordinate.
- Functional regression:
  - `Read Aloud`, `Stop`, paragraph selection, contents navigation, section navigation, and theme switching still work.
  - `npm run type-check`
  - `npm run build`

## Assumptions
- Desktop is already functionally acceptable and only needs refinement, not a structural rewrite.
- Mobile should prioritize reading space over always-visible metadata.
- The redesign should stay within the existing visual language rather than introducing a new brand/theme direction.
